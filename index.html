1.1

Create an AKS cluster and connect with kubectl

Create the shared AKS cluster, connect kubectl, inspect the system namespace, and deploy the first workload.

Foundational 45 min ▾
◎ What you need to know
  • AKS manages the control plane; the Free tier has no SLA, while paid tiers add an API-server SLA.
  • AKS creates a node resource group named like MC_rg-aks-labs_aks-lab_eastus2; do not edit those VMSS/NIC/disk resources directly.
  • New clusters use managed identity by default; service principals are legacy or explicit and require secret rotation.
  • The first pool is commonly agentpool, and nodes carry kubernetes.azure.com/agentpool=agentpool.
  • Azure CNI Overlay uses VNet IPs for nodes and overlay IPs for pods; AKS supports up to 250 pods/node where configured.
  • konnectivity is the current AKS API tunnel component; old tunnelfront references are legacy.
  • az aks install-cli installs kubectl; az aks get-credentials only writes kubeconfig.

Prerequisites: Azure CLI signed in with permission to create rg-aks-labs and an AKS cluster in eastus2.

Create the cluster
  1. Search Kubernetes services → + Create → Create a Kubernetes cluster.
  2. Basics: Resource group rg-aks-labs, Cluster name aks-lab, Region East US 2, Preset Dev/Test, Pricing tier Free.
  3. Node pools: keep system pool agentpool, VM size Standard_DS2_v2, node count 2, autoscaling off.
  4. Networking: choose Azure CNI Overlay and keep default service CIDR, DNS service IP, and Standard load balancer.
  5. Integrations: keep managed identity. Monitoring: skip Container insights for now.
  6. Review + create → wait for validation → Create. Expect roughly 8-15 minutes.
Connect
  1. Open aks-lab → Connect → Cloud Shell; run the generated az aks get-credentials command.
  2. Run kubectl get nodes -o wide, then open Kubernetes resources → Workloads to see the same API data in the portal.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2

az group create -n "$RG" -l "$LOC"
az aks create -g "$RG" -n "$AKS" -l "$LOC" \
  --node-count 2 \
  --node-vm-size Standard_DS2_v2 \
  --tier free \
  --generate-ssh-keys \
  --network-plugin azure \
  --network-plugin-mode overlay

az aks get-credentials -g "$RG" -n "$AKS" --overwrite-existing
kubectl get nodes -o wide

az aks show -g "$RG" -n "$AKS" \
  --query "{name:name,location:location,tier:sku.tier,nodeRG:nodeResourceGroup,identity:identity.type,k8s:kubernetesVersion}" -o table
# kubectl & YAML
kubectl cluster-info
kubectl get pods -n kube-system -o wide
kubectl get pods -n kube-system | egrep 'coredns|konnectivity|metrics-server|csi|ip-masq' || true
kubectl get nodes --show-labels

kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: aks-hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: aks-hello
  template:
    metadata:
      labels:
        app: aks-hello
    spec:
      containers:
      - name: aks-hello
        image: mcr.microsoft.com/azuredocs/aks-helloworld:v1
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: aks-hello
spec:
  selector:
    app: aks-hello
  ports:
  - port: 80
    targetPort: 80
EOF

kubectl rollout status deployment/aks-hello
kubectl get all -l app=aks-hello -o wide
⚠ Traps & gotchas
  • Editing resources in the MC_* node resource group is unsupported and can be reconciled over by AKS.
  • Free tier is not a production SLA answer; it has no financially backed control-plane uptime guarantee.
  • Deleting the node resource group removes the VMSS, NICs, and disks the cluster needs to function.
  • SSH keys do not mean direct node SSH is the normal path; use kubectl, az aks command invoke, or approved node-shell workflows.
Cleanup / teardown
# Keep the shared cluster. Remove only the sample workload.
kubectl delete service aks-hello --ignore-not-found
kubectl delete deployment aks-hello --ignore-not-found

Add user pools, taints and spot capacity

Add regular and spot user pools, protect the system pool with a taint, and schedule pods with selectors and tolerations.

Core 40 min ▾
◎ What you need to know
  • Every AKS cluster needs at least one System pool; system pools host critical add-ons and cannot scale to 0.
  • User pools run application workloads and can scale independently, including to 0 when no required pods are pinned there.
  • CriticalAddonsOnly=true:NoSchedule is optional on system pools, not default.
  • Spot pools must be User mode, have no SLA, are evictable, and get kubernetes.azure.com/scalesetpriority=spot:NoSchedule automatically.
  • --max-pods is chosen at pool creation; common defaults are kubenet 110, Azure CNI classic 30, and overlay up to 250.
  • Each node pool maps to a VM Scale Set; use az aks nodepool instead of direct VMSS edits.
  • Kubernetes labels such as kubernetes.azure.com/agentpool=apps affect scheduling; Azure resource tags do not.

Prerequisites: The shared aks-lab cluster exists and your kubeconfig context points to it.

Add the apps pool
  1. Open Kubernetes services → aks-lab → Node pools → + Add node pool.
  2. Name apps, Mode User, VM size Standard_DS2_v2, Node count 2, autoscaling off, label workload=apps.
Add the spot pool
  1. Node pools → + Add node pool → Name spot, Mode User, enable Spot, Eviction policy Delete, Max price -1, Node count 1.
Taint the system pool
  1. Portal coverage for taint editing varies; use Cloud Shell with the CLI command to apply CriticalAddonsOnly=true:NoSchedule to agentpool.
  2. Return to Node pools and compare Mode, Priority, node count, labels, and taints for all three pools.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2

az aks nodepool add -g "$RG" --cluster-name "$AKS" -n apps \
  --mode User --node-count 2 --node-vm-size Standard_DS2_v2 \
  --labels workload=apps --max-pods 110

az aks nodepool add -g "$RG" --cluster-name "$AKS" -n spot \
  --mode User --priority Spot --eviction-policy Delete --spot-max-price -1 \
  --node-count 1 --node-vm-size Standard_DS2_v2 --labels workload=spot

az aks nodepool update -g "$RG" --cluster-name "$AKS" -n agentpool \
  --node-taints CriticalAddonsOnly=true:NoSchedule

az aks nodepool list -g "$RG" --cluster-name "$AKS" \
  --query "[].{name:name,mode:mode,count:count,priority:scaleSetPriority,maxPods:maxPods,taints:nodeTaints}" -o table
# kubectl & YAML
kubectl get nodes -L kubernetes.azure.com/agentpool,kubernetes.azure.com/scalesetpriority,workload
kubectl describe nodes | egrep 'Name:|Taints:|agentpool|scalesetpriority' || true

kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: spot-demo
spec:
  nodeSelector:
    kubernetes.azure.com/scalesetpriority: spot
  tolerations:
  - key: kubernetes.azure.com/scalesetpriority
    operator: Equal
    value: spot
    effect: NoSchedule
  containers:
  - name: web
    image: nginx:1.27
EOF

kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: apps-demo
spec:
  nodeSelector:
    kubernetes.azure.com/agentpool: apps
  containers:
  - name: web
    image: nginx:1.27
EOF

kubectl get pods spot-demo apps-demo -o wide
kubectl describe pod spot-demo | sed -n '/Node-Selectors:/,/Events:/p'
⚠ Traps & gotchas
  • Spot workloads need both a selector/affinity and a toleration; the toleration alone does not attract pods to spot nodes.
  • Adding the system taint makes ordinary pods Pending unless they target user pools or tolerate the taint.
  • You cannot scale the only System pool to zero; create a User pool for disposable capacity.
  • Changing max pods later usually means creating a replacement pool and moving workloads.
Cleanup / teardown
kubectl delete pod spot-demo apps-demo --ignore-not-found
# Keep pools for later labs. Optional:
# az aks nodepool delete -g rg-aks-labs --cluster-name aks-lab -n spot --yes
# az aks nodepool delete -g rg-aks-labs --cluster-name aks-lab -n apps --yes

Upgrade Kubernetes and node images

Inspect available AKS upgrades, distinguish control-plane, node-pool, and node-image upgrades, and configure maintenance-aware automation.

Core 40 min ▾
◎ What you need to know
  • Node pools can be up to 2 minor versions behind the control plane, or 3 with AKS LTS where supported.
  • AKS Kubernetes upgrades are one-way; downgrades are not supported.
  • az aks upgrade --control-plane-only updates the managed API server without upgrading node pools.
  • az aks nodepool upgrade --node-image-only patches node OS images without changing Kubernetes version.
  • Node upgrades drain pods and honor PDBs; too-strict PDBs can stall or fail the upgrade when drain cannot evict pods.
  • --max-surge defaults to about 10%; higher values require vCPU and IP quota but reduce maintenance time.
  • Auto-upgrade channels include none, patch, stable, rapid, and node-image.
  • Maintenance schedule types include aksManagedAutoUpgradeSchedule and aksManagedNodeOSUpgradeSchedule.

Prerequisites: The cluster is healthy and the subscription has quota for any surge nodes used during upgrade.

Cluster version
  1. Open Kubernetes services → aks-lab → Settings → Cluster configuration.
  2. Review the current Kubernetes version and upgrade picker. Do not start a production upgrade without a tested target version.
Node pools
  1. Open Node pools → select a pool → review Kubernetes version, node image version, and upgrade options.
Maintenance windows
  1. Open Settings → Maintenance configurations. Create separate windows for cluster upgrades and node OS/image upgrades when policy requires it.
  2. During a live upgrade, keep Node pools, Workloads, and Cloud Shell kubectl get nodes -w open.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2

az aks get-upgrades -g "$RG" -n "$AKS" -o table
az aks get-versions -l "$LOC" -o table

TARGET_VERSION=""
if [ -n "$TARGET_VERSION" ]; then
  az aks upgrade -g "$RG" -n "$AKS" --kubernetes-version "$TARGET_VERSION" --control-plane-only --yes
  az aks nodepool upgrade -g "$RG" --cluster-name "$AKS" -n agentpool \
    --kubernetes-version "$TARGET_VERSION" --max-surge 33% --yes
fi

az aks nodepool get-upgrades -g "$RG" --cluster-name "$AKS" -n agentpool -o table
az aks nodepool upgrade -g "$RG" --cluster-name "$AKS" -n agentpool --node-image-only --max-surge 33% --yes

az aks update -g "$RG" -n "$AKS" --auto-upgrade-channel patch
az aks update -g "$RG" -n "$AKS" --node-os-upgrade-channel SecurityPatch
az aks show -g "$RG" -n "$AKS" --query "{k8s:kubernetesVersion,auto:autoUpgradeProfile.upgradeChannel,nodeOS:autoUpgradeProfile.nodeOSUpgradeChannel}" -o table
# kubectl & YAML
kubectl get nodes -o wide
kubectl get pods -A -o wide

kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: upgrade-pdb-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: upgrade-pdb-demo
  template:
    metadata:
      labels:
        app: upgrade-pdb-demo
    spec:
      containers:
      - name: web
        image: nginx:1.27
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: upgrade-pdb-demo
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: upgrade-pdb-demo
EOF

kubectl rollout status deployment/upgrade-pdb-demo
kubectl get pdb upgrade-pdb-demo
kubectl get pods -l app=upgrade-pdb-demo -o wide
# Run while upgrading: kubectl get nodes -w
⚠ Traps & gotchas
  • Control-plane-only does not upgrade worker nodes; validate both API and node versions after maintenance.
  • A single-replica app with minAvailable: 1 blocks voluntary eviction and can fail a drain.
  • Rapid auto-upgrade is not a production stability default; patch or stable is usually the safer answer.
  • High surge values fail when subnet IPs or regional vCPU quota are insufficient.
Cleanup / teardown
kubectl delete pdb upgrade-pdb-demo --ignore-not-found
kubectl delete deployment upgrade-pdb-demo --ignore-not-found

Stop, start, scale and choose tiers

Pause AKS safely, resume it, scale pools, and select Free, Standard, or Premium based on SLA and support requirements.

Foundational 30 min ▾
◎ What you need to know
  • az aks stop stops the managed control plane and deallocates nodes; workloads do not run until az aks start completes.
  • Cluster identity and state are preserved, but dynamic LoadBalancer public IPs are not the same guarantee as static IP resources.
  • User pools can scale to 0; System pools must keep capacity for critical add-ons.
  • Free tier has no SLA; Standard has 99.9%, or 99.95% with availability zones where supported.
  • Premium adds long-term support options, commonly 2 years for supported Kubernetes versions.
  • Documented scale is up to 5000 nodes per cluster on Standard tier and 1000 on Free tier.
  • Stopped clusters should not be left stopped for very long periods because certificates and platform maintenance can age out.

Prerequisites: The shared cluster is running. Do not stop it if other labs are active.

Power state
  1. Open Kubernetes services → aks-lab → Overview.
  2. Click Stop only in an approved window; click Start and expect several minutes before nodes return to Ready.
Scale pools
  1. Open Node pools → select apps → Scale node pool → set count 1, then return to 2.
Pricing tier
  1. Open Cluster configuration → compare Free, Standard, and Premium. Use Cloud Shell to verify powerState and tier.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2

az aks show -g "$RG" -n "$AKS" --query "{state:powerState.code,tier:sku.tier,pools:agentPoolProfiles[].count}" -o json

# Use only when no one needs the lab cluster.
# az aks stop -g "$RG" -n "$AKS"
# az aks start -g "$RG" -n "$AKS"

az aks scale -g "$RG" -n "$AKS" --node-count 2
if az aks nodepool show -g "$RG" --cluster-name "$AKS" -n apps >/dev/null 2>&1; then
  az aks nodepool scale -g "$RG" --cluster-name "$AKS" -n apps --node-count 1
  az aks nodepool scale -g "$RG" --cluster-name "$AKS" -n apps --node-count 2
fi

az aks update -g "$RG" -n "$AKS" --tier standard
az aks update -g "$RG" -n "$AKS" --tier free
# kubectl & YAML
kubectl get nodes -o wide
# During start/scale operations: kubectl get nodes -w

kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scale-watch
spec:
  replicas: 3
  selector:
    matchLabels:
      app: scale-watch
  template:
    metadata:
      labels:
        app: scale-watch
    spec:
      containers:
      - name: web
        image: nginx:1.27
EOF

kubectl rollout status deployment/scale-watch
NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
kubectl cordon "$NODE"
kubectl drain "$NODE" --ignore-daemonsets --delete-emptydir-data --force
kubectl get pods -l app=scale-watch -o wide
kubectl uncordon "$NODE"
⚠ Traps & gotchas
  • Stopping AKS makes the API server and workloads unavailable; it is not the same as scaling one Deployment to zero.
  • Dynamic Service IPs can change after recreation; use static IP resources for stable inbound endpoints.
  • Manual drain without --ignore-daemonsets stalls on DaemonSet-managed pods.
  • Free tier plus zone-spread nodes still does not create a control-plane SLA.
Cleanup / teardown
kubectl delete deployment scale-watch --ignore-not-found

Create zone-resilient node pools

Create a zone-spanning pool, verify zone labels, spread replicas, and identify storage and load-balancer zone implications.

Advanced 35 min ▾
◎ What you need to know
  • Node-pool zones are set with --zones 1 2 3 and are immutable; changing zones requires a replacement pool.
  • Current topology label is topology.kubernetes.io/zone; beta failure-domain labels are legacy.
  • Standard Load Balancer supports zonal and zone-redundant front ends; Basic is not the current production AKS answer.
  • Azure Disk LRS is zonal and pins attached pods to one zone; ZRS disks support cross-zone scenarios where available.
  • topologySpreadConstraints uses maxSkew, topologyKey, and whenUnsatisfiable.
  • DoNotSchedule enforces spread; ScheduleAnyway scores spread but still schedules if needed.
  • A PDB protects voluntary disruption with settings such as minAvailable: 4; it does not survive a full zone outage by itself.

Prerequisites: eastus2 supports availability zones and you have quota for a three-node user pool.

Add a zonal pool
  1. Open Kubernetes services → aks-lab → Node pools → + Add node pool.
  2. Name zapps, Mode User, VM size Standard_DS2_v2, Node count 3, Availability zones 1, 2, 3, label workload=zonal.
  3. After creation, note there is no simple edit path for zones; replacement pools are the migration pattern.
Verify placement
  1. Use Cloud Shell for the kubectl pane, then open Workloads and confirm six replicas are running.
  2. Inspect disks or load balancers in the node resource group only to read zone settings; do not edit AKS-owned resources there.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2

az aks nodepool add -g "$RG" --cluster-name "$AKS" -n zapps \
  --mode User --node-count 3 --node-vm-size Standard_DS2_v2 \
  --zones 1 2 3 --labels workload=zonal

az aks nodepool show -g "$RG" --cluster-name "$AKS" -n zapps \
  --query "{name:name,zones:availabilityZones,labels:nodeLabels}" -o json
# kubectl & YAML
kubectl get nodes -L topology.kubernetes.io/zone,kubernetes.azure.com/agentpool,workload

kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: zonal-web
spec:
  replicas: 6
  selector:
    matchLabels:
      app: zonal-web
  template:
    metadata:
      labels:
        app: zonal-web
    spec:
      nodeSelector:
        workload: zonal
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: zonal-web
      containers:
      - name: web
        image: nginx:1.27
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: zonal-web
spec:
  minAvailable: 4
  selector:
    matchLabels:
      app: zonal-web
EOF

kubectl rollout status deployment/zonal-web
kubectl get pods -l app=zonal-web -o wide
kubectl get pdb zonal-web
⚠ Traps & gotchas
  • You cannot edit a pool from zones 1/2 to 1/2/3; build a new pool and drain workloads.
  • Zone-spread stateless pods do not fix single-zone LRS disk attachment for stateful pods.
  • Hard topology spread with too few eligible zones leaves pods Pending.
  • A PDB controls voluntary evictions, not power, storage, or network loss in a zone.
Cleanup / teardown
kubectl delete pdb zonal-web --ignore-not-found
kubectl delete deployment zonal-web --ignore-not-found
# Optional quota recovery:
# az aks nodepool delete -g rg-aks-labs --cluster-name aks-lab -n zapps --yes

Manage kubeconfig and cluster access

Merge credentials, switch contexts, understand admin and Entra formats, and use command invoke when direct API access is blocked.

Core 30 min ▾
◎ What you need to know
  • az aks get-credentials merges into ~/.kube/config; --overwrite-existing replaces an existing context entry.
  • KUBECONFIG can point to a separate file for automation or isolated lab work.
  • kubectl config get-contexts, use-context, and current-context prevent wrong-cluster operations.
  • --admin downloads local cluster-admin credentials and is blocked when local accounts are disabled.
  • Entra clusters can use --format azure and kubelogin for exec-auth kubeconfig entries.
  • az aks command invoke runs inside the cluster and needs Microsoft.ContainerService/managedClusters/runCommand/action.
  • az aks rotate-certs is disruptive; refresh kubeconfig after rotation.

Prerequisites: The shared cluster exists. Install kubelogin if testing Entra exec-auth conversion.

Connection commands
  1. Open Kubernetes services → aks-lab → Connect and review the generated Azure CLI commands.
  2. Open Access control (IAM) → My access and confirm you have rights to read the cluster and run command invoke if needed.
  3. Open Settings → Authentication and authorization and note local account and Azure RBAC settings.
Locked clusters
  1. For private API servers or firewall restrictions, launch Cloud Shell or use az aks command invoke to run kubectl get nodes from Azure.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2

az aks get-credentials -g "$RG" -n "$AKS" --overwrite-existing
kubectl config get-contexts
kubectl config current-context

mkdir -p .kube-lab
az aks get-credentials -g "$RG" -n "$AKS" --file .kube-lab/config --overwrite-existing
KUBECONFIG=.kube-lab/config kubectl get nodes

# Admin credentials may be disabled by policy.
# az aks get-credentials -g "$RG" -n "$AKS" --admin --overwrite-existing

az aks install-cli || true
az aks get-credentials -g "$RG" -n "$AKS" --format azure --overwrite-existing
kubelogin convert-kubeconfig -l azurecli || true

az aks command invoke -g "$RG" -n "$AKS" --command "kubectl get nodes -o wide"
# kubectl & YAML
kubectl config get-contexts
kubectl config current-context
kubectl auth can-i get pods -A
kubectl auth can-i '*' '*' --all-namespaces

kubectl apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: lab16-access
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: context-check
  namespace: lab16-access
data:
  cluster: aks-lab
EOF

kubectl get configmap context-check -n lab16-access -o yaml
kubectl delete namespace lab16-access
⚠ Traps & gotchas
  • Running destructive kubectl commands before checking current-context damages the wrong cluster.
  • --admin is not always available and should not replace RBAC-aware Entra access.
  • Private cluster connection failures can be network path issues even when kubeconfig is correct.
  • Certificate rotation invalidates old credentials and can cause downtime during the operation.
Cleanup / teardown
kubectl delete namespace lab16-access --ignore-not-found
rm -rf .kube-lab

2.1

Roll out and roll back Deployments

Create a Deployment, scale it, update its image, inspect ReplicaSet history, and roll back to a known revision.

Foundational 35 min ▾
◎ What you need to know
  • A Deployment owns ReplicaSets; do not edit ReplicaSets directly because the Deployment controller reconciles desired state.
  • Default strategy is RollingUpdate with maxSurge: 25% and maxUnavailable: 25%.
  • revisionHistoryLimit defaults to 10, which controls how many old ReplicaSets remain for rollback.
  • kubectl rollout undo deployment/name --to-revision=N rolls back to a specific stored revision.
  • kubernetes.io/change-cause is shown in kubectl rollout history when you annotate changes.
  • Old ReplicaSets normally remain with desired/current 0; that is rollback history, not duplicate capacity.
  • Recreate terminates old pods before creating new ones and is for incompatible or single-writer workloads, not zero-downtime web tiers.

Prerequisites: Shared cluster aks-lab is running and kubeconfig is configured.

Create from the portal
  1. Open Kubernetes services → aks-lab → Kubernetes resources → Workloads.
  2. Click + Create → Apply a YAML and paste the namespace, Deployment, and Service YAML for lab21.
  3. Open Deployments → web and inspect desired pods, available pods, labels, and related ReplicaSets.
Watch rollout
  1. Use Cloud Shell to run kubectl set image, rollout status, history, and undo.
  2. Open Pods and sort by Created time. New pods appear under the new ReplicaSet while old pods drain to 0.
# Azure CLI (bash)
RG=rg-aks-labs
AKS=aks-lab
LOC=eastus2
NS=lab21

az aks get-credentials -g "$RG" -n "$AKS" --overwrite-existing
kubectl create namespace "$NS" --dry-run=client -o yaml | kubectl apply -f -
kubectl -n "$NS" create deployment web --image=nginx:1.27 --replicas=2
kubectl -n "$NS" annotate deployment web kubernetes.io/change-cause="initial nginx 1.27" --overwrite
kubectl -n "$NS" expose deployment web --port 80 --target-port 80
kubectl -n "$NS" scale deployment web --replicas=4
kubectl -n "$NS" rollout status deployment/web
kubectl -n "$NS" get deploy,rs,pods,svc -o wide
# kubectl & YAML
NS=lab21
kubectl create namespace "$NS" --dry-run=client -o yaml | kubectl apply -f -

kubectl apply -n "$NS" -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  annotations:
    kubernetes.io/change-cause: initial nginx 1.27 deployment
spec:
  replicas: 3
  revisionHistoryLimit: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:

Expose services deliberately

Foundational 40 min ▾
◎ What you need to know

Choose the right CNI

Compare kubenet, Azure CNI node-subnet and Azure CNI Overlay address behavior, capacity math and migration options before choosing a production networking model.

Advanced 45 min ▾
◎ What you need to know
  • kubenet assigns pods from a private pod CIDR and NATs through node IPs; it depends on route tables and has a practical 400-node route-table scale limit.
  • Microsoft has announced kubenet retirement on March 31, 2028; new AKS clusters should use Azure CNI Overlay or another current Azure CNI mode.
  • Azure CNI node-subnet gives every pod a VNet IP. Subnet sizing is nodes x max-pods plus upgrade surge; with 50 nodes and default 30 pods, reserve at least 1,500 pod IPs before system overhead.
  • Azure CNI Overlay gives nodes VNet IPs and pods IPs from a private overlay CIDR, default 10.244.0.0/16, conserving VNet addresses and supporting a default 250 pods per node.
  • Overlay pods are not directly reachable from the VNet; expose them with Kubernetes Services, LoadBalancers, ingress or other routed entry points.
  • Cilium dataplane is selected with --network-dataplane cilium; it uses eBPF and includes NetworkPolicy enforcement through --network-policy cilium.
  • Overlay creation uses --network-plugin azure --network-plugin-mode overlay --pod-cidr; classic node-subnet CNI uses --network-plugin azure without overlay mode.
  • Migration support changes: kubenet-to-overlay in-place update is supported, and node-subnet-to-overlay has supported paths in current AKS releases, but always check the current AKS support matrix for your Kubernetes version, dataplane and policy engine.

Enforce least-privilege pod traffic

Build a NetworkPolicy-enabled AKS cluster, apply default-deny ingress and egress, then allow only frontend-to-backend HTTP and DNS traffic.

Advanced 40 min ▾
◎ What you need to know
  • With no NetworkPolicy selecting a pod, Kubernetes allows all ingress and all egress for that pod; policy enforcement starts only after a policy engine exists.
  • AKS policy engines include Azure NPM, Calico and Cilium; the engine is selected with --network-policy azure|calico|cilium, often at cluster create time or through supported upgrade paths.
  • podSelector: {} means all pods in the policy namespace; an omitted selector is invalid, while an empty selector is intentionally broad.
  • policyTypes: [Ingress, Egress] matters: an ingress-only policy does not restrict egress, and an egress-only policy does not restrict ingress.
  • NetworkPolicies are additive unions; one allow policy cannot deny traffic allowed by another policy. There is no priority order in standard Kubernetes NetworkPolicy.
  • Egress default-deny breaks DNS until you allow UDP and TCP 53 to kube-dns or CoreDNS in namespace kube-system.
  • Namespace selectors can match the built-in label kubernetes.io/metadata.name, which is safer than hand-labeling system namespaces.
  • Azure-to-Cilium and other enablement paths have changed over time; historically many policy choices were create-time, so check the current AKS support matrix before promising in-place changes.

4.1

Persist data on Azure Disks

Create Azure Disk PVCs with built-in and custom storage classes, prove pod rescheduling preserves data, and expand a volume online.

Core 40 min ▾
◎ What you need to know
  • Azure Disk CSI built-in classes include managed-csi for Standard SSD and managed-csi-premium for Premium SSD; kubectl get storageclass is the source of truth for your cluster defaults.
  • The key Azure Disk fact: an Azure Disk is ReadWriteOnce and attaches to one node at a time, so it is for single-writer pods, not shared multi-pod file storage.
  • volumeBindingMode: WaitForFirstConsumer delays disk creation until a pod is scheduled, which places the disk in the pod's zone and avoids zone mismatch failures.
  • Immediate binding can create a disk before the scheduler chooses a node; in zonal clusters this can pin the PVC to a zone with no available pod capacity.
  • Default reclaim policy is commonly Delete: deleting the PVC deletes the underlying managed disk. Use Retain when data must survive PVC deletion.
  • Expansion requires allowVolumeExpansion: true; you can grow from 4Gi to 8Gi online, but Kubernetes does not shrink PVCs.
  • Custom disk classes can set skuName: Premium_ZRS for zone-redundant disks where region and AKS support allow it.
  • VM size limits cap disk count: for example, Standard_DS2_v2 supports 8 data disks, which can cap how many RWO PVC pods fit on one node.

Share storage with Files and Blob

Mount one Azure Files RWX claim into multiple pods, verify shared writes, and understand when Blob CSI is a better fit than SMB files.

Core 40 min ▾
◎ What you need to know
  • azurefile-csi provisions Azure Files over SMB and supports ReadWriteMany, which lets multiple pods mount the same share concurrently.
  • Azure Files SMB is convenient for shared config and simple content, but metadata-heavy workloads can be slow because every stat/list operation crosses the network.
  • Azure Files NFS uses a custom StorageClass with protocol: nfs, requires Premium FileStorage, and relies on network rules/private endpoints rather than SMB key auth.
  • The CSI driver commonly stores the storage account key in a Kubernetes Secret in the claim namespace; inspect secrets when mounts fail or when rotating storage keys.
  • Common SMB mount options include dir_mode=0777, file_mode=0777, mfsymlinks, cache=strict and nosharesock; set permissions deliberately.
  • Blob CSI can be enabled with az aks update --enable-blob-driver and provides classes such as azureblob-fuse-premium and azureblob-nfs-premium.
  • Blobfuse2 is best for read-heavy analytics and object data; it is not a full POSIX filesystem, so rename may be copy-like and hard links are not available.
  • Decision shortcut: Disk = fastest RWO block for one pod, Files = RWX SMB/NFS shared file semantics, Blob = object storage mounted for analytics or legacy file-like access.

◎ What you need to know

Scale pods from CPU requests

Create an autoscaling/v2 Horizontal Pod Autoscaler, drive CPU load, and watch replicas scale out and back in from requests.

Core 35 min ▾
◎ What you need to know
  • AKS includes metrics-server by default; HPA needs resource metrics unless you add custom or external metrics adapters.
  • autoscaling/v2 supports Resource, Pods, Object, and External metric types.
  • CPU utilization target is a percentage of container requests.cpu, not limits and not node CPU; no request gives <unknown>.
  • Default HPA sync period is 15s; default scale-down stabilization window is 300s.
  • minReplicas defaults to 1; HPA scale-to-zero needs alpha behavior, so use KEDA for production zero.
  • maxReplicas is required and caps runaway scale even when metrics stay above target.
  • The formula is ceil(currentReplicas * currentMetric / targetMetric), then stabilization and behavior are applied.
  • Behavior policies use Pods or Percent, periodSeconds, and selectPolicy Max, Min, or Disabled.
  • Do not continuously set spec.replicas on a Deployment managed by HPA; GitOps can fight the controller.

6.5

Walk the failure ladder

Create common pod failures, diagnose each with events, logs, and debug commands, then apply the smallest fix.

Core 45 min ▾
◎ What you need to know
  • Triage order is kubectl get pods → describe pod events → logs --previous → exec → debug.
  • Pending means not scheduled or waiting; ImagePullBackOff is image retry; CrashLoopBackOff is repeated exit.
  • CrashLoopBackOff backs off from about 10s to 5m; --previous shows the last failed container.
  • OOMKilled is usually exit code 137 with lastState.terminated.reason=OOMKilled.
  • Pending causes include insufficient CPU/memory, unbound PVC, taint mismatch, and nodeSelector or affinity with no matching node.
  • Image pull events show 401/403 auth, 404/manifest unknown tag errors, or DNS/network reachability failures.
  • kubectl debug node/<n> -it --image=mcr.microsoft.com/cbl-mariner/busybox:2.0 mounts the host at /host.
  • Ephemeral containers use kubectl debug pod/<pod> --target <container> for distroless images without shells.
  • AKS checks include az aks show --query provisioningState, Diagnose and solve problems, Resource Health, and cluster-info dump.

Prerequisites: Shared cluster aks-lab, namespace lab65, and comfort deleting intentionally broken pods.

Status and events
  1. Open Kubernetes services → aks-lab → Workloads → Namespace lab65 and group pods by Status.
  2. Select a failed pod → Events. The newest warning usually names image 404, missing ConfigMap, failed scheduling, or OOM.
AKS diagnostics
  1. Open Diagnose and solve problems → review Cluster health, Node health, Connectivity, and Performance.
  2. Open Resource health and compare Azure platform health with Kubernetes object failures; a green resource can still have bad YAML.
Debug safely
  1. Use Cloud Shell for kubectl debug; it is usually better than SSH for node inspection.
